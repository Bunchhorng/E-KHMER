# E-KHMER Order & Payment Audit

## Executive Summary

Orders are created only through checkout, with item, price, variant, address,
shipping, and payment snapshots stored on the order aggregate. This audit
strengthens the financial and audit boundaries around that flow: coupon usage
is now concurrency-safe, status history records the actor and prior state, and
coupon administration rejects invalid discount values.

## Orders

### Status: PASS (container verification pending)

- Orders are created inside checkout's transaction after cart, stock, shipping,
  coupon, and total calculation checks.
- Order numbers are generated by the dedicated `OrderNumberGenerator` and
  checked for collisions.
- Customer order access is scoped by owner; guest lookup is scoped by the
  stored session fingerprint.
- Admin listings support server-side pagination, status filtering, and search
  by order number/customer/email.

## Order Items

### Status: PASS (container verification pending)

- Each item snapshots product name, variant label, SKU, image, unit price,
  quantity, line total, and shop ID.
- Historical orders do not depend on subsequent catalog edits.

## Order Status and History

### Status: PASS (container verification pending)

- The central `OrderService` enforces the allowed lifecycle transitions.
- Cancellation/refund returns reserved or deducted stock exactly once based on
  the original order state.
- Tracking events now include `from_status` and `changed_by`, in addition to
  the destination status, note/description, and timestamp.
- Admin transition notes are stored in the status history.

## Payments and Payment Transactions

### Status: NEEDS WORK for external-provider settlement

- Payment amount is derived only from the calculated order total.
- Confirmation locks the order and rejects a second settlement, preventing a
  second inventory deduction or capture transaction.
- Successful online sandbox settlement writes a capture transaction; refunds
  write one refund transaction and restore stock.
- Production blocks self-confirmed online payments until a verified provider
  callback/webhook integration exists.

## Coupons and Coupon Usage

### Status: PASS (container verification pending)

- Coupon validation covers active windows, usage limit, per-user limit,
  minimum subtotal, fixed/percentage discount, and maximum discount.
- Redemption now locks the coupon row before revalidating and incrementing the
  use count, preventing concurrent checkouts from exceeding limits.
- `coupon_usages.order_id` is unique, preventing duplicate consumption for one
  order.
- Cancellation, refund, and expired reservation release coupon capacity.
- Admin validation requires a positive discount, restricts percentage coupons
  to 100 or less, requires positive usage limits, and rejects an expiry before
  the start date.

## Checkout, Inventory, Shipping, and Notification Integration

- Checkout reserves stock atomically, and confirmation deducts it only once.
- Cancellation and refund release or restore inventory depending on whether
  stock was merely reserved or already deducted.
- Shipping state is synchronized during order status transitions.
- Customers receive order-status notifications for supported lifecycle events.

## Security Improvements

- Financial totals, discount, shipping, payment amount, and payment status are
  not accepted from the browser.
- Order ownership, guest session access, and admin authorization remain
  server-side.
- Coupon use-count updates and per-order usage creation are serialized under a
  database lock.
